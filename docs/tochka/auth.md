# Авторизация и разрешения

**Ловушка первая: токен не один.** Токен Open Banking открывает `tochka-api`, `info` и
`express-credit`. Для `cyclops`, `medusa` и `pay-gateway` продукт подключается отдельно, и
доступ к ним общий токен не даёт — они и живут на других хостах.

В SDK это выражено явно:

```python
from tochka import Client, Config
from tochka.types import Product

config = Config(
    token="открытый-банкинг",
    product_tokens={Product.CYCLOPS: "токен-номинальных-счетов"},
)
```

Продукт без своего токена берёт основной — так что обычная интеграция ничего не настраивает.

## Как токен доезжает до запроса

Заголовок `Authorization: Bearer <токен>` ставит клиент, для каждого запроса выбирая токен
по продукту метода. Руками его передавать не нужно и не следует: `Authorization` — в списке
заголовков, которые генератор выкидывает из параметров методов (`SKIP_HEADER_PARAMS`).

Два способа получить токен описаны в доке банка: **OAuth 2.0** (когда действуете от имени
клиента) и **JWT‑токен** (когда от своего имени). SDK не добывает токен — он его принимает.

## Разрешения

Каждый метод требует своё разрешение; в спецификации они объявлены полем «Необходимые
разрешения». Что встречается и сколько операций закрывает:

| Разрешение | Операций | Что открывает |
|---|---|---|
| `ReadSBPData` | 15 | чтение по СБП: QR‑коды, статусы, ТСП |
| `EditSBPData` | 11 | регистрация и изменение QR‑кодов, ТСП, возвраты |
| `ManageInvoiceData` | 9 | счета на оплату |
| `MakeAcquiringOperation` | 8 | создание платёжных ссылок, списания, возвраты |
| `ReadAcquiringData` | 6 | чтение операций эквайринга |
| `ReadCustomerData` | 3 | данные клиента |
| `ReadBalances` | 3 | балансы счетов |
| `ReadStatements` | 3 | выписки |
| `CreatePaymentForSign` | 3 | платёжные поручения на подпись |
| `ReadAccountsBasic` / `ReadAccountsDetail` | 2 + 2 | список счетов и детали |
| `CreatePaymentOrder` | 1 | платёжное поручение |

Ещё 9 операций разрешения не требуют, а у `cyclops`, `medusa` и `pay-gateway` спека их не
объявляет вовсе — там доступ определяется подключением продукта.

Полный перечень разрешений выдаётся при подключении приложения; методы вебхуков требуют
`ManageWebhookData` — это сказано в доке банка, но в спецификации не проставлено.

**Отказ по разрешению выглядит как 403** и приезжает типизированной ошибкой:

```python
from tochka import PermissionDeniedError

try:
    await client.get_balance_info(account_id=...)
except PermissionDeniedError as error:
    error.code       # AccessDenied
    error.message    # что именно не разрешено
    error.error_id   # идентификатор для поддержки
```

## Что нельзя делать

**Не кладите токен в код и в репозиторий.** `Config` принимает его аргументом — читайте из
окружения или секрет‑хранилища. У SDK нет и не будет чтения `.env` за вас: молчаливый
подхват переменной окружения — это способ уехать в прод с чужим ключом.

**Не переиспользуйте боевой токен в песочнице.** Песочница — другой базовый URL
(`sandbox/v2/`), и SDK переключается на него через `Environment.SANDBOX`; если у продукта
тестового сервера нет (`pay-gateway`), SDK бросит `ConfigurationError`, а не уйдёт молча в
прод.
